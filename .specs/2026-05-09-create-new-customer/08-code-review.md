## Findings

### F-R-001 — `CustomerExceptionHandler` is not scoped to the customer feature (should-fix)

**Category:** Architecture / Spring idioms
**File:** `sdd-api/src/main/java/com/loiane/sdd/customer/CustomerExceptionHandler.java`
**Lines:** 13

`@RestControllerAdvice` with no `basePackageClasses` or `assignableTypes` argument registers a global handler that intercepts exceptions from **every** controller in the application. When a second feature is added (e.g. `OrderController`), an `Exception` thrown there will be caught and returned as a 500 by this handler — potentially masking the second feature's own handler or returning misleading error bodies.

The design doc scopes this handler to the `customer` feature only, and ADR-001 explicitly isolates features. Narrowing the advice now prevents a hard-to-debug ordering conflict later.

**Suggested fix:**
```java
@RestControllerAdvice(assignableTypes = CustomerController.class)
class CustomerExceptionHandler {
```
This keeps the advice package-private and limits its catch scope to exactly `CustomerController`.

### F-R-002 — `CustomerService` carries redundant `@Valid` + `@Validated` but the `@Valid` on the method parameter is unreachable without a proxy (should-fix)

**Category:** Spring idioms / correctness
**File:** `sdd-api/src/main/java/com/loiane/sdd/customer/CustomerService.java`
**Lines:** 8, 17

`@Validated` on the class enables method-level constraint validation via a Spring AOP proxy. The `@Valid` annotation on the `create` method parameter (`@Valid CustomerRequest request`) triggers that proxy when the method is called from outside the class (i.e. from `CustomerController`). This is technically correct and works.

However, the same constraints are already enforced upstream by `@Valid @RequestBody` in `CustomerController`. The double-validation is not harmful but it adds confusion: a reader must understand that `@Validated` on the service means "Spring wraps this in a proxy for JSR-380 enforcement", and they must ask whether this is intentional or defensive duplication. If the service is ever called from a non-controller context (e.g. a batch job) without going through the controller's `@Valid`, the service-level validation correctly catches that case. If that secondary path exists, document it with a comment; if it does not, prefer removing the service-level `@Valid`/`@Validated` to reduce surprise.

**Suggested fix (if the service is only ever called from the controller):**
Remove `@Validated` from the class and `@Valid` from the parameter. Leave the validation solely on `CustomerController`. Add a comment on the controller's `@Valid` explaining why it is the single enforcement point.

**If a non-controller call path exists or is anticipated:**
Keep `@Validated`/`@Valid` and add a Javadoc comment explaining the intent.

This is a should-fix because the current code is correct but silently doubles the cost of every valid create call and will surprise the next reader.

### F-R-003 — `CustomerService.setId` uses `Field.setAccessible(true)` to inject the primary key in a unit test (nit)

**Category:** Test quality / clarity
**File:** `sdd-api/src/test/java/com/loiane/sdd/customer/CustomerServiceTest.java`
**Lines:** 68–72

The test uses reflection to force a value into the package-private `id` field of `Customer`, because the entity has no setter or constructor for `id`. This is a reasonable workaround given that `id` is generated by the database and not settable by application code. However, it makes the test fragile: a rename of the field from `"id"` to anything else breaks the test at runtime, not compile time.

A constructor-only approach (accepting an `id` parameter that is used exclusively in tests) or a protected no-arg constructor + a static factory method would eliminate the reflection. Alternatively, since `Customer` is package-private and the test is in the same package, a package-private setter `void setId(Long id)` used only in tests is the simplest compile-time-safe fix.

**Suggested fix:**
Add a package-private `void setId(Long id) { this.id = id; }` to `Customer.java`. Replace the reflection block in the test with `saved.setId(42L)`.

### F-R-004 — Angular `PHONE_PATTERN` regex uses character class with an unescaped `-` that works by accident (nit)

**Category:** Correctness / clarity
**File:** `sdd-ui/src/app/customer/customer-create/customer-create.ts`
**Line:** 13

```typescript
const PHONE_PATTERN = /^[0-9 +()\-]*$/;
```

The `-` inside the character class is escaped as `\-`, which is valid but nonstandard. The idiomatic form is to place `-` at the start or end of the character class: `[0-9 +()\-]` vs `[0-9 +() -]` or `[-0-9 +()]`. This is not a bug — `\-` is interpreted as a literal hyphen — but it can mislead a reader into thinking a range is intended. The spec allows `+`, `(`, `)`, `-` which is exactly what is matched.

**Suggested fix:** Move the hyphen to the end: `/^[0-9 +()\-]*$/` → `/^[0-9 +() -]*$/` or keep `\-` but add a comment that it is a literal hyphen, not a range.

### F-R-005 — `CustomerCreate.onSubmit()` casts `form.value` to `CustomerRequest` unsafely (nit)

**Category:** Correctness / clarity
**File:** `sdd-ui/src/app/customer/customer-create/customer-create.ts`
**Line:** 57

```typescript
this.customerService.create(this.form.value as CustomerRequest).subscribe(...)
```

`form.value` for a reactive form with all controls enabled returns `{ firstName: string | null, ... }` — Angular types every control value as `T | null`. The `as CustomerRequest` cast suppresses TypeScript's null checks. In practice, `onSubmit()` is only reachable when `form.valid` is true (the button is disabled when `form.invalid`), and all required fields pass validation before that, so no field will actually be null at this point.

The cast is defensible but silently disables the type system for this call. A safer alternative uses `form.getRawValue()` (which preserves null in the type) or constructs the request object explicitly from control values.

**Suggested fix:**
```typescript
const request: CustomerRequest = {
  firstName: this.firstName.value!,
  lastName: this.lastName.value!,
  email: this.email.value!,
  phone: this.phone.value || null,
  company: this.form.controls.company.value || null,
};
this.customerService.create(request).subscribe(...);
```

## Praise

**P-001 — 100% line and branch coverage on the customer package**
JaCoCo reports 64/64 lines and 2/2 branches. Both handler branches (`isServerError` true/false) are exercised. The coverage is genuine, not padded by trivially-weak assertions.

**P-002 — `data-testid` attributes on every form element**
Using `data-testid` attributes decouples the tests from CSS class names and Material DOM structure. This is the right approach for Angular Material components where the rendered HTML can vary between library versions.

**P-003 — Race-condition 409 explicitly tested**
`createReturns409ForDataIntegrityViolation` in `CustomerControllerTest` and `handleDataIntegrity` in `CustomerExceptionHandler` address the TOCTOU gap between the proactive `existsByEmail` check and the `repository.save()` call. This is above the minimum required by the spec and reflects good defensive thinking.

**P-004 — `CustomerRepositoryIT` verifies the schema via `DatabaseMetaData`**
Testing that the Flyway migration produced the correct column list and the named unique index `uk_customer_email` is an excellent integration test. It catches migration drift that JPA unit tests alone would not.

**P-005 — `toApiError` separates server errors from field errors cleanly**
The Angular service returns a typed `CustomerApiError` with a boolean `isServerError` flag, avoiding magic status-code comparisons in the component. The component branches on the flag without knowing HTTP status codes — a clean separation of concerns.
